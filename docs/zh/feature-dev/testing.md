# 测试与工作类型

测试是 Spec 得以执行的机制。链条是:

```text
需求 + 验收标准 → 测试计划 → 测试
```

## 从 Spec 推导测试

每条验收标准至少对应一个测试;业务规则和边界情况补充其余:

```text
验收标准                          测试
- 正确账号密码可以登录        →   登录成功
- 错误密码登录失败            →   错误密码被拒绝
- 被禁用账号不能登录          →   禁用账号被拒绝
```

如果一条标准无法转化为测试,它就还不是标准 —— 重写它,直到可观察。

## 测试正确的东西

- 使用项目已有的测试框架、结构和风格。
- 测外部行为,不测内部结构:输入与可观察的输出、HTTP 响应、渲染结果、持久化状态
  —— 而不是私有方法。
- 宁可少而有意义,不求穷尽分支;先覆盖标准、规则和边界。
- 保持测试确定性。

## 每步都测

增量开发路线图为每一步指明测试。在每步之前或同时写好测试,落地时运行,修复直到
通过。所有步骤完成后,运行项目的全量验证命令(`docs/TESTING.md`),让别处的回归在
宣布完成之前暴露。

## 工作类型

**Bug 修复**

```text
用失败测试复现 → 修复 → 测试通过 → 检查同类问题
```

没有先写失败测试的 Bug 修复只是猜测。如果 Bug 无法直接复现,尽可能接近,并在 Spec
中记录差距。

**重构 / 技术债**

```text
确认行为覆盖率 → 需要时补回归/特征化测试
→ 小步重构 → 每步后验证行为不变
```

如果某个行为没有测试,先写一个捕获它当前行为的测试,再改内部结构。绝不把重构和
行为变更混在一起 —— 拆成独立的功能。

**依赖升级**

盘点新版本破坏了什么(破坏性变更、移除的 API、配置格式),升级,跑全量测试,修复
善后,并在 Spec 和文档中记录行为变化。

## 评审与文档同步

完成之前,通读完整 diff:它做到了 Spec 所说、且不多做吗?错误路径处理了吗?命名和
结构与项目惯例一致吗?

文档保持真实,否则比没有更糟。当实现改变了行为、接口、数据或架构时,受影响的文档
—— `docs/API.md`、`docs/DATABASE.md`、`docs/ARCHITECTURE.md` 和 Spec —— 在同一处
工作中更新:

```text
文档 ↔ Spec ↔ 测试 ↔ 代码
```

然后在 `specs/ROADMAP.md` 中把功能标记为 `Done`。
