# project-dev

交付一项开发工作 —— 功能、变更、Bug 修复、重构、技术债或依赖升级 —— 把达成一致的
Spec 变成经过验证的代码,并与项目文档保持同步。Foundry 的核心循环在这里完整运行:

```text
访谈 → Spec → 实施计划 → 测试 → 编码 → 验证 → 同步文档
```

## 何时触发

- "按照工作流实现 F001。"
- "修复这个 Bug:……"、"重构 auth 模块且不改变行为。"、"升级 React 到 19。"、
  "偿还导出模块的技术债。"

它**不会**为只读评审或诊断触发,不会为启动新项目([`project-start`](../project-start/))
或恢复缺少文档的仓库([`project-onboard`](../project-onboard/))触发,也不会为独立验证
整个项目与文档的一致性触发([`project-verify`](../project-verify/))。

## 工作流

```text
功能请求
    ↓
1. 读项目文档             README、docs/*、specs/ROADMAP.md
    ↓
2. 读相关代码             这次请求触及的模块和测试
    ↓
3. 访谈用户               解决 Spec 中由用户决定的缺口
    ↓
4. 填写 / 完善 Feature Spec   目标、需求、验收标准
    ↓
5. 写实施计划               小的垂直切片
    ↓
6. 推导测试               来自验收标准
    ↓
7. 逐步实现               运行每步的测试,修复直到通过
    ↓
8. 评审变更               对照 Spec 通读完整 diff;跑全量测试
    ↓
9. 在 GitHub 上交付       GitHub 模式:推分支、开 PR、跟进 CI 与评审
    ↓
10. 同步文档              更新因此失真的一切
```

值得深入的两个部分有单独页面:

- [Spec 与访谈](./spec) —— Spec 如何填写、什么值得问。
- [测试与工作类型](./testing) —— 推导测试,以及 Bug / 重构 / 升级的入口差异。

## 工作类型,同一个循环

`project-dev` 刻意不按工作类型分裂成独立流程。变化的只是入口:

- **Bug 修复** —— 先用失败测试复现,再修复直到通过。
- **重构 / 技术债** —— 确认行为覆盖率,缺测试就补回归测试,小步重构,逐步验证
  行为不变。
- **依赖升级** —— 盘点破坏点,升级,跑全量测试,记录行为变化。

## GitHub 模式

当 Roadmap 记录了 `Collaboration: GitHub — enabled` 时,交付经由平台进行,而不是
停在本地工作区:

- 请求可能以 issue 形式到达;issue 及其评论作为需求输入读入,并链接到 Spec 的
  `Tracking` 节。
- 工作发生在以 Spec 命名的分支上(`F003-short-urls`),实施计划的每一步一个提交。
- 本地验证通过后,智能体推分支并开出 PR:Spec 的 Goal、验收标准清单、测试证据,
  以及 `Closes #<issue>`。PR 的 CI 检查计入验证 —— CI 红意味着工作尚未完成。
- 评审意见以新提交的形式回流到 Spec 和计划。凭常设授权,CI 全绿、必需评审通过后
  智能体即可合并;绝不合并红的 PR。
- 文档同步与 Roadmap 状态翻转(`In Progress` → `In Review` → `Done`)随 PR 提交,
  合并即生效,关联的 issue 自动关闭。

## 硬性规则

强制项很少;留下的这些定义了 Foundry:

- 仍然存在**由用户决定**的 Spec 问题(行为、业务规则、成功标准、约束)时,
  **禁止开始实现**。
- 验证**必须**从 Spec 推导 —— 测试来自验收标准。
- 实现**必须**运行相关测试;失败意味着工作尚未完成。
- **必须**保留工作区中与本次无关的用户改动。
- 除非 Roadmap 启用了 GitHub 协作或用户明确授权该操作,**禁止**远程写操作
  (推送、issue、PR、milestone、看板)。
- **禁止**合并 CI 检查未通过的 pull request。force 操作、删除分支、发布 release
  和部署,始终需要逐次明确授权。
