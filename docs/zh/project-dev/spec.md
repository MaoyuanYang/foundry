# Spec 与访谈

Feature Spec(`specs/F<nnn>-<slug>.md`)是用户与智能体之间的约定:要构建什么、它如何
行为、如何验证完成。它来自四个来源 —— 绝不只来自请求文本:

```text
项目文档 + 已有代码 + 用户请求 + 用户访谈 → Feature Spec
```

## 填写 Spec

读完项目文档和相关代码后,智能体逐章节扫描 Spec 模板,先从请求、仓库和低风险
工程判断填入一切已经可以确定的内容,再列出剩余的缺口。判断每个缺口的标准:

> 答案属于用户 —— 产品行为、业务规则、成功标准、硬约束 —— 就去问;属于仓库
> 就去读;是低风险的实现细节,就自行决定并记录。

文档定义必须理解什么;访谈补齐由用户决定的缺口。

## 好的访谈

- 每轮只问少量相关问题;答案会让后面的问题失效。
- 具体优于抽象:"过期的会话应该返回 401 还是静默刷新?" —— 而不是"错误应该怎么
  处理?"
- 给出最佳猜测作为默认:"我会返回 401 并让刷新可选 —— 可以吗?"
- 绝不为用户决定的问题编造答案;Spec 里的错误假设会变成代码里的错误功能。
- 重要性只调节深度,不决定入口:在用户决定的缺口中,先问影响行为、实现或测试
  的那些;次要的给出默认建议即可。

当每个重要章节都有可靠来源、剩余未知全部由智能体决定且低风险时,访谈即告完成。
每个开放问题通过询问解决,回答后即删除。

## Spec 模板

```text
# Feature: <名称>

## Goal                          这个功能解决什么问题
## Background                    背景:已有行为、相关文档
## User Flow                     用户或调用方如何使用
## Requirements                  要实现的行为,以可观察的方式陈述
## Business Rules                约束行为的重要规则
## Edge Cases                    失败与边界情况
## UI / UX                       仅适用于有 UI 影响的功能
## API / Data Changes            仅当接口或数据变化时
## Acceptance Criteria           清晰、可验证的完成标准
## Implementation Plan           小步计划,每步可测试
## Test Plan                     验收标准如何被验证
## Open Questions                尚未解决的、由用户决定的问题
```

不适用的章节直接删除。仍然含有模板引导文字的 Spec 不算完成。

产出物随变更规模缩放:当请求只有一个可观察行为、没有未决问题、也没有超出该行为的
接口或数据模型变更时,一份简短的变更记录(Goal、Acceptance Criteria、所做决策)就
足够了 —— 跳过空章节和多步计划。测试先行、验证与文档同步仍然适用。拿不准时,
写完整 Spec。

## 实施计划

编码之前,Spec 会获得一个分步计划,回答一个问题:*这件事应该以什么顺序被构建和
验证?*(符合上述简短变更记录的改动不需要实施计划 —— 它的单一步骤就是计划。)每
一步有目标、范围、测试和验证方式。优先**垂直切片** —— 每一步以可工作、可测试的
行为结束:

```text
Step 1  最小可工作的 happy path
Step 2  第一条核心业务规则
Step 3  错误路径和边界情况
Step 4  集成与文档同步
```

避免按技术层拆分(先写所有 Entity、再所有 Repository、再所有 Service)—— 那样的步骤
直到最后才能验证。实施计划是计划,不是合同:当实现揭示更好的拆分或错误的假设时,
更新实施计划和 Spec,然后继续。

## Roadmap 状态

功能进行中时,`specs/ROADMAP.md` 将其标记为 `In Progress`;工作验证完成、文档同步后,
标记为 `Done`。
