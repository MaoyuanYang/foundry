# 常见问题

## 通用

**这些 Skill 会自动帮我写代码吗?**
`project-start` 和 `project-onboard` 产出文档,在业务代码之前停止。只有 `project-dev`
写代码,而且是在 Spec 中由用户决定的问题解决、测试从验收标准推导之后。
`project-verify` 可能补充仅用于验证的测试或检查脚本,让文档承诺变得可检查 ——
绝不是业务代码。

**我想做重构、升级或技术债清理怎么办?**
直接对 `project-dev` 提出 —— "重构 auth 模块且不改变行为。"循环与任何功能相同,
只是入口不同:重构从确认行为覆盖率开始(缺测试就补回归测试),升级从盘点破坏点
开始。会改变可观察行为的"重构"是变更而不是重构 —— 拆成独立的功能。

**MVP 完成了,怎么规划下一波功能?**
在已有文档的项目上再进入 `project-start`:它就新方向访谈,然后添加 Roadmap 条目和
草稿 Spec。不需要独立流程 —— 规划与实现本来就由不同 Skill 分开。

**为什么我刚打开一个新仓库时 `project-onboard` 不触发?**
设计如此。onboarding 写文档且不改行为,因此需要明确意图。打开或浏览陌生仓库属于
只读问答,除非你明确要求接管并恢复基线。

**`project-verify` 和 `project-onboard` 有什么区别?**
`project-onboard` 修复*缺少文档或文档不可信*的仓库,把它恢复成基线:它编写和修复
文档。`project-verify` 审计*已有文档*的项目:它核查文档的承诺与现实是否一致并记录
发现 —— 除了补充仅用于验证的检查,它不改动任何东西。先恢复,后验证。

**什么时候该运行 `project-verify`?**
只要文档的可信度重要的时候:发布之前、一批功能完成之后、onboarding 之后,或者当
Roadmap 声称工作已 `Done` 而你想要证据而非声称时。它报告带严重程度和建议后续工作的
发现;修复交给 `project-dev`。

**Foundry 会在我的项目里创建协调文件吗?**
不会。项目状态就是文档集(`README.md`、`docs/`、`specs/`)—— 没有状态文件、没有
元数据、没有需要维护的簿记。移除 Foundry 后留下的是一个正常的仓库。

## GitHub 协作

**Foundry 必须用 GitHub 吗?**
不。整个循环完全本地运行 —— 单人、离线、GitLab 或任何其他环境都可以。GitHub 模式
是可选的一层,由记录在 `specs/ROADMAP.md`(`## Tracking`)中的一个决定启用。参见
[工作流 —— 在 GitHub 上团队协作](../workflow)。

**这个决定什么时候做?**
项目初始化时做一次:只要 GitHub 远端和已认证的 `gh` CLI 同时存在,`project-start`
和 `project-onboard` 就会询问是否启用 GitHub 协作。答案记录在 Roadmap 的
`## Tracking` 中,后续 Skill 直接读取记录,不再重复询问。没有记录的已有文档项目会被
补问一次,然后落档。

**智能体会自己合并 pull request 吗?**
只有当 Roadmap 启用了协作、且 PR 的 CI 检查全绿、必需评审通过时才会 —— 并且绝不
合并红的 PR。force 操作、删除分支、发布 release 和部署,始终需要逐次明确授权。

**GitLab 或其他平台怎么办?**
Skill 保持平台无关:没有 GitHub 环境时以本地模式运行,零远程操作。镜像到其他平台
不是内建能力;你自己的工具可以读取同样的文档。

## 工作流

**智能体一直问我问题,怎么让它停下?**
访谈是文档驱动的:先扫描模板,从你所说的、仓库和工程判断填入内容,智能体只问
由用户决定的缺口 —— 目标、用户、范围、规则、成功标准、约束。如果它在问琐事,直接
说 —— 或回答"用你的判断",智能体会把决策记入 Spec 并继续。

**实现中发现 Spec 是错的怎么办?**
更新 Spec,然后继续。实施计划和 Spec 是计划,不是合同;当现实不一致时,文档在同一处
工作中改变。这就是原则 7:文档与实现保持同步。

**这是严格的 TDD 吗?**
这是 Spec 驱动的测试:测试从验收标准推导,在每个实现步骤之前或同时编写,且必须在
工作完成前通过。它不规定红-绿-重构的仪式 —— 它规定"没有运行过验证的步骤不算完成"。

**Foundry 能和我们团队的 tracker 和 PR 流程一起用吗?**
可以 —— 在 GitHub 上它们更是一等公民。项目启动时启用协作后,issue、pull request、
CI 检查、milestone 和 Projects 看板镜像 Roadmap 与 Spec,而文档仍是真相源。在其他
平台或纯本地,Skill 塑造工作如何被规格化、规划、测试和记录,你的工具原样叠加即可。

**Foundry 支持哪些语言?**
Skill 对代码语言无关。它们从仓库读取你项目的惯例,遵循已有的测试框架和风格。生成的
项目文档默认英文:`project-start`(以及在无文档仓库上的 `project-onboard`)会与你
确认一次文档语言,之后的工作跟随文档的语言。
