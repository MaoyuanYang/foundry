# project-verify

文档定义了应当为真的事情;`project-verify` 检查它是否确实为真。面向一个已有文档和
Roadmap 的项目,对照文档的承诺验证其现状,然后给出有证据支撑的发现报告。产出是发现
报告,而不是修复:修复和实现属于 [`feature-dev`](../feature-dev/)。

## 何时触发

- "对照文档验证当前项目。"
- "审计 Roadmap 里标记 `Done` 的功能是否真的完成了。"
- "发布前检查文档是否仍然符合现实。"

它**不会**为实现或修复任何东西而触发([`feature-dev`](../feature-dev/)),不会为创建或
修复项目文档而触发([`coding-start`](../coding-start/) /
[`project-onboard`](../project-onboard/)),也不会为普通问答和只读的代码讲解而触发。

## 工作流

```text
有文档的项目
    ↓
1. 收集文档的承诺        README、PRODUCT、ARCHITECTURE、TESTING、适用的补充文档、
                          ROADMAP 状态、Done / In Progress 的 Spec
    ↓
2. 推导验证范围          清单由文档定义 —— 没有通用清单
    ↓
3. 运行声明的验证        严格按文档运行 build / test / lint 命令
    ↓
4. 检查 Done 的功能      验收标准 vs 可执行证据
    ↓
5. 实测关键用户流程      PRODUCT 的核心用例,含跨功能边界的流程
    ↓
6. 对照文档与现实        只在意图不明时询问用户
    ↓
7. 补充仅用于验证的检查  证据缺失处;不改任何行为
    ↓
8. 报告发现并停止        发现报告;修复交给 feature-dev
```

## 范围来自文档

没有固定、通用的清单要跑。项目自己的文档定义验证范围:文档做出了十条承诺,就检查这
十条。每条承诺得到一个结果标签:

- **Verified(已验证)**—— 存在可执行证据且通过。
- **Broken(已证伪)**—— 存在证据,且证据表明承诺不成立。
- **Unverified(未验证)**—— 无法产生可执行证据。

一个标记为 `Done` 的功能,如果其验收标准没有可执行证据,那就是一条发现,而不是通过。
当让承诺变得可检查需要补一个测试或检查脚本时,这是允许的 —— 仅用于验证,绝不是业务
行为变更。

## 产出什么

| 产物 | 内容 |
|---|---|
| `docs/VERIFICATION.md` | 已验证的承诺、带证据和严重程度的发现、未能实测的项 |
| 仅用于验证的测试 / 检查脚本 | 仅在文档承诺缺少可执行证据时补充 |
| `specs/ROADMAP.md` | 应用户要求,把需要处理的发现记为 `Draft` 条目 |

每条发现写明问题是什么、观察到的证据、哪份文档或 Spec 做出了承诺、严重程度和建议的
后续工作 —— 但修复是 `feature-dev` 的工作,不是验证的工作。

## 边界

- 不做修复、不改业务行为;允许补充仅用于验证的测试和检查脚本,保持清晰隔离并记录。
- 验证期间不修复文档 —— 差异就是发现,报告因此保持独立审计的立场,而不是漂移的一方。
- 未经用户明确授权,不执行破坏性或远程操作。
