# maintenance-dev —— 战役与切片

一个战役如何分解为可验证、可交付的切片。

## 切片属性

每个切片**最小**（一个结构步骤）、**独立可验证**（其回归范围单独可通过）、**独立可交付**（任意完成前缀后战役仍可合并）、**可回滚**（记录了逆转方式）、**有序**（顺序与依赖记录在案；一个战役内切片并行不在范围内）。

## `REFACTOR`：不改行为的结构改善

用证据命名结构目标（那个循环依赖、那个巨型服务、那片重复，file/line 级引用）。选择目标边界和最小的移动序列——绞杀者式渐进提取优于大爆炸重写，纯删除步骤放最后。每次移动一个切片：提取 → 重指消费者 → 移除旧路径，中间状态需要保持可验证时拆成独立切片。

## `DEBT`：消费债务登记表

每个计划清理的行都引用债务登记表（`docs/onboarding/KNOWLEDGE_GAPS.md` 或项目等价物）中的 Debt ID；没有登记的行先补登记，绝不静默修复。按表面与风险分组；按解锁价值和爆炸半径排序。编码缺陷的行拆出去：行为修复是候选 `feature-dev` Bug；本战役只补特性化测试和结构性治理。完成的行标记为已解决并附证据链接——绝不静默删除。

## `UPGRADE`：分阶段版本迁移

1. 记录当前与目标版本、lockfile 策略（locked/frozen 模式；lockfile 提交与代码移动分开）和环境矩阵。
2. 从 release notes、弃用警告、类型/契约差异构建破坏性变更清单。逐项分类：`no code impact`、`mechanical fix`、`behavioral`、`blocked`。行为性条目需要 Decision Authority 接受或转 `feature-dev` Change；`blocked` 条目可记录原因后推迟升级。
3. 大跨度升级分层推进：工具链 → 直接依赖 → 传递依赖 lockfile 收敛 → 代码适配。每层一个或多个切片，各自验证。
4. 记录回滚方式：钉回旧 lockfile/ref；破坏性步骤记录其逆转。
5. Major Tech Choice（新数据库引擎、新框架家族、新运行时）是 **L3 决策**：任何切片之前需要具名 Architecture Decision Authority 和处于实现授权状态的 ADR。

## `CAMPAIGN_PLAN` 清单

`Roadmap Status: READY` 之前 11 项全部满足：战役类型/目标/不变量带证据；最小有序切片；每个切片的表面被安全网覆盖；每个切片的回归范围；无混杂动机（第二动机记为候选工作项）；`DEBT` 行引用 Debt ID；`UPGRADE` 清单完整；L3 选择有 ADR；无已批准行为变更；任意前缀后可交付；`SAFETY NET READY` 清单未失效。

## 战役中纪律

一次一个切片，验证后再下一个。范围发现（表面比计划多、计划外依赖）会重开计划：修订并重验证受影响门禁，或把新范围拆成候选战役——绝不静默扩张。合并前执行标准集成协议：与基线同步、重跑记录的集成切片与回归范围、记录证据。
