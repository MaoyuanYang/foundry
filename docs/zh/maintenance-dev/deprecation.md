# maintenance-dev —— 弃用与移除

退役是维护流程中唯一**有意**改变可观察行为的一支——因此它的权限链条是全套件最严格的。

## 退役 vs 重构

移除能力不是重构。`REFACTOR`/`DEBT`/`UPGRADE` 保持行为；`RETIRE` 用一个经显式批准的"不存在"替换行为。"清理一下"、"删掉"、"关掉"、"不再支持"某能力的请求是 `RETIRE` 战役；结构工作中顺带发生的移除属于分类错误，必须停下重新分类。

## 退役计划

| 要素 | 要求 |
|---|---|
| 退役能力 | 精确边界：API 端点、UI 表面、事件、配置键、数据、文档——带证据命名 |
| 预期行为变更 | 退役后精确的可观察行为（错误响应、移除、替代指引） |
| 权限确认 | 具名 Decision Authority 确认了预期行为变更；执行 Agent 绝不自批 |
| 消费者 | 每个内部/外部消费者带证据标签枚举 |
| 迁移 | 每个消费者：迁移、无消费者、或接受破坏（每个接受都需各自的权限确认） |
| 公告 | 受众、渠道、内容——含权限要求的兼容期 |
| 回滚 | 移除切片的逆转方式 |
| 历史 | 退役能力的 Roadmap 条目与交付记录标记 `DEPRECATED`/退役，绝不删除 |

## 弃用阶段

```text
DEPRECATE（公告 + 兼容路径）
  -> MIGRATE（消费者迁移；按计划的兼容期）
  -> REMOVE（移除切片，最后执行）
  -> SYNC（文档与登记表更新）
```

无消费者或权限接受立即移除时，`DEPRECATE` 和 `MIGRATE` 可记录为空操作——记录理由，绝不默认。兼容期内弃用路径保持行为一致；提前削弱它就是未批准的行为变更。移除切片把能力、测试、文档条目一起删除；遗留死路径记为后续 `DEBT` 候选，而非静默吸收。

## 验证

`RETIRE` 的逐切片 `BEHAVIOR PRESERVED` 含义是"差异恰好等于批准的预期行为变更，且没有其他变化"——对照退役前路径的特性化证据加标准回归范围验证。数据按计划处理：归档（记录位置与逆转）、只读保留、或在显式授权的破坏性动作下删除。

## STOP 条件

- 退役计划缺少具名 Decision Authority 对预期行为变更的确认。
- 某消费者状态为 `UNKNOWN` 且无法从证据解决——隐藏消费者是经典的移除事故；绝不在推断上移除。
- 破坏接受或破坏性数据动作缺少各自的显式权限确认。
- 兼容期或公告渠道未决。
